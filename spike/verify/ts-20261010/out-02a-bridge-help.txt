#!/usr/bin/env node
/**
dsh-sdk-bridge —— 从 Windows 侧驱动 WSL 里的 dsh SDK（stdio JSON-RPC 2.0）。

Node 要求：**>=26.10**（零构建：本文件走 Node 原生 type stripping，直接 `node dsh-sdk-bridge.ts` 即可，
不需要 tsc / dist / 任何构建步骤；因此只使用**可擦除**语法——type / interface / 类型注解 / `as` / 泛型，
禁用 enum、namespace、构造函数参数属性、`import x = require()`）。

与 invoke-wsl-dsh.ps1（L1 一次性问答：`dsh headless "<task>"`）的区别：
  · 本桥走 **常驻 SDK 通道** `dsh --profile sdk`：同一进程可多轮（`--prompt` 追加轮次）；
  · `--session <id>` 只用于**同一进程内**复用 id。**跨进程**复用同一 id 会被服务端拒绝：
    `JSON-RPC -32603: session "<id>" already exists`（2026-10-10 实测）⇒ 跨进程续接要靠上层
    编排（一个会话配一个长驻运行时），不能靠"重开进程 + 同 id"。
  · stdout 只承载协议帧（NDJSON JSON-RPC 2.0），答案要从 `session.event` 里折叠；
  · 无 cancel / 无 per-prompt 结果（协议明确的设计限制）：放弃一轮 = 关掉运行时进程。

为什么值得这一层（2026-10-10 取证）：
  · SDK/ACP 是 dsh 的编程接入面：方法仅 initialize / session/prompt / shutdown；
    通知 session.event / session.status / subagent.started / subagent.finished；
  · 工具执行、MCP（stdio 子进程）、skills、文件写入**全部发生在 host 进程所在 OS** ——
    host 在 WSL，则这些就都隔离在 WSL，契合「Windows 只做展示与交互」。

版本一致性（本桥自己强制，不靠上游）：
  真相源 = 桌面 `resources/runtime/primary-runtime/runtime.json` 的 `desktopVersion`；
  pin 落 WSL `~/.dsh/.desktop-version-pin`；不一致 ⇒ 用桌面版本并告警。
  依据：跨宿主协议层**无版本协商**（SDK 的 serverInfo.version 硬编码 "0.0.1" 且客户端不校验），
  而包层由 dsh-app-boot 按 peerDependencies 严格求值 —— 版本错配只会静默禁用插件，不报错。

用法：
  node dsh-sdk-bridge.ts "任务文本" [--prompt "第二轮"] [--prompt "第三轮"]
       [--cwd /home/g/project/xxx] [--session <id>] [--provider deepseek-official]
       [--model deepseek-flash] [--profile sdk|sdk-minimal] [--distro debian-u8-1]
       [--timeout-sec 600] [--dsh-version X] [--json] [--debug] [--no-pin]
