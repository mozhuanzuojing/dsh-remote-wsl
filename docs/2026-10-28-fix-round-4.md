## 修了什么

### 1. A-P1-A（P1，根因级）：provider/model 只对新起守护生效

**问题**：`launchScript()` 已经会拼 `--provider/--model`（上一轮 `41734ec`），但守护是 detached 常驻进程。
用户改完配置、重启 DSH 后，`ensureDaemon()` 命中的是**复用**路径：`configCompat()` 只比对
`cwd/profile/idleMs/queueLimit/lingerMs` + 协议/插件版本，**不比对 provider/model**；而 `meta` / `status` /
`hello` 也**不上报**这两个字段，`prompt` 载荷只有 `key/text/cwd`。结果：旧守护继续用旧 provider 打上游 ——
症状与上一轮的 401 完全相同，且零告警、用户无法从 `wsl_status` 判断。

**修法**（把"守护实际生效的 provider/model"变成**可观测 + 可判定**的东西）：

| 层 | 改动 |
|---|---|
| 守护身份 | `meta` / `status` / `hello` 三处同时上报 `provider` / `model` / `useShellEnvironment` / `proxyPort`（`src/daemon.ts`） |
| 复用判据 | `configCompat()` 比对：守护上报值与本次配置不同 ⇒ **hard**（拒绝复用，明确要求 `wsl_daemon action=restart`）；旧守护未上报 ⇒ **soft**（无法校验，提示 restart 后可核对，不硬阻塞）；`useShellEnvironment` / `proxyPort` 不同 ⇒ soft（`src/daemon-launch.ts`） |
| 最后一道闸门 | `prompt` 请求携带宿主当前 provider/model，守护不一致 ⇒ 明确拒绝（`ok:false` + `retryable:false` + `configMismatch`），**不创建 key、不跑旧 provider**（`src/daemon.ts`、`src/daemon-protocol.ts`） |
| 可见面 | `wsl_status` 的 daemon 行与 `wsl_daemon status` 增加 `provider=` / `model=`；不一致/未上报时输出 `daemon route: ⚠️ …` 告警（`src/register-tools.ts`） |
| 协议 | `PROTOCOL_VERSION` 2 → 3（字段是加法的：新宿主 + 旧守护仍可用，走 soft 提示） |

> 为什么 hard 而不是 soft：provider/model 决定这一轮能不能打到正确的上游，与 `cwd` / `profile` 同一量级；
> soft 只会重复"配置改了像没改"。旧守护缺字段时无法判定 ⇒ 才退 soft。

### 2. A-P2-B（P2，安全）：启动脚本的 shell 注入面

`launchScript()` 原来用 `JSON.stringify` 把 `cfg.wslHome` / `cfg.cwd` / `cfg.profile` / `cfg.provider` /
`cfg.model` / `state-dir` / `launcher` 拼进**双引号**，`--version` 更是裸插值。`JSON.stringify` 只保证
"一个 shell 词"，**不保证字面量** —— bash 双引号内 `$()` / 反引号仍会展开（复核时已实测）。
现统一改走 `shq()`（POSIX 单引号 + `'\''`，本仓 `src/shell-quote.ts` 既有实现），与 systemd 路径的
"数据走 argv / 单引号"纪律一致；`--version` 也走 `shq()`。

### 3. A-P2-D（P2，健壮性）：空值 provider/model/profile

`normalizeConfig()` 现在与 `distro/wslHome` 同一套归一：`provider: ''`、`model: '  '`、`profile: '\t'`
⇒ 显式回落 `DEFAULTS`，不再把空串原样送进守护（`??` 对空串不生效是原缺陷）。

## 升级提示

- **旧守护（0.3.4 之前）不会上报 provider/model**：升级宿主后第一次 `wsl_status` 会出现
  `daemon route: ⚠️ 守护没有上报实际 provider/model … ⇒ wsl_daemon action=restart 后可核对`。
  执行一次 `wsl_daemon action=restart`（会丢当前会话上下文）即可让新守护带字段重启。
- **改了 provider/model 之后**：老版本需要手动 restart 且没有任何提示；0.3.4 起 `wsl_agent` 会**直接报错**
  并告诉你 restart（不会被旧守护静默跑一轮）。

## 补修：A-P2-E（v0.3.5，同日追加）

原先把 A-P2-E 判为"设计取舍、不在本轮范围"，用户明确要求只修这一条后补上：

**问题**：探测结论是进程级缓存（成功与失败都缓存），并在启动期冻结进配置对象。DSH 启动时 WSL 冷启动/卡住
⇒ 首次探测失败 ⇒ 本进程所有入口都报"没有目标"，只能重启 DSH。

**修法**（不改变"整进程缓存"的既有设计，只加一个**用户主动触发**的重探入口）：

| 层 | 改动 |
|---|---|
| `config.ts` | 归一化时记录**探测前的显式原值**（Symbol，不参与 JSON）；新增 `refreshAutoTarget(config, {probe})`：清进程缓存 → 按显式原值重算 → **原地**写回同一份配置对象（`distro`/`wslHome`/`cwd` + 探测结论），返回 `{ok, problem, notes, previous, current, changed, auto}` |
| 工具面 | `wsl_status` 新增可选参数 `redetect: boolean`：为 `true` 时先重探再出整段状态；成功/失败都如实回报；`wsl_daemon status` 的空目标报错里直接给出这个入口 |
| 提示 | 目标未解析时，`wsl_status` 输出 `hint: 可调用 wsl_status({ redetect: true }) …`；普通调用**绝不**触发探测（保持只读/廉价） |
| 测试 | 新增 `test/redetect-target.test.ts`（5 条：失败→成功、再次失败、显式不覆盖、只显式 distro、**缓存必须被清**）；`test/target-guards.test.ts` 增加 2 条工具接线用例（含"无参不重探"） |

**边界（写进 README，不藏）**：
- 只对**宿主侧**消费方立即生效（`wsl_exec` / `wsl_agent` / `wsl_status` / 面板 / daemon）。
- `wsl` agent preset 的文件/搜索子插件是**注册时配置快照**，仍需重启 DSH 才跟随 —— 重探成功的输出里会明说。
- 显式配置的 `distro` / `wslHome` / `cwd` 永不被探测结果覆盖。

**版本**：0.3.4 → **0.3.5**（协议不变：这次只改宿主侧行为 + 工具参数）。

**验证（实跑）**：`check-syntax` 29 TS + 13 JS OK；Windows `node --test` **151 tests / 139 pass / 0 fail / 12 skipped**；
WSL Debian 同套 **151 / 151 pass / 0 skipped**（新增 7 条：`redetect-target` 5 + 工具接线 2）。
