这一轮接着 `docs/2026-10-27-fix-round.md`（两轮、60 条缺陷）与 HANDOFF 的「Next Steps」，处理**上一轮
明确留下的缺口 + 本轮新发现的伪成功**。一句话结论：**上一轮声称"已实现"的供应链校验当时是死代码**，

## 1. 供应链校验（**本轮最重要**）

### 上一轮的说法与实测事实
`docs/2026-10-27-fix-round.md` 第 2 行写着「解析发布页的 `*.sha256` / `SHA256SUMS` / `checksums.txt`，
下载后校验 sha256；不匹配拒绝安装」。**当时这是假的**：全仓只有 3 处 `checksum` 命中，且
`asset.checksumUrl` / `asset.checksumName` **没有任何赋值处** —— `if (asset.checksumUrl)` 恒为假，
`verified` 永远是 `'unavailable'`。也就是说：**插件自动下载并执行的每一个二进制，从未被校验过**，
而文档与提交信息都声称已实现。属于「伪成功 / 静默降级」类缺陷。

### 现在真做了什么
- `resolveAssetAsync()` / `resolveAsset()` 现在**真的解析**校验来源：
  1. GitHub API 资产的 `digest`（`sha256:<hex>`，服务端算好的，最权威）；
  2. 同批发布里的校验资产：`<asset>.sha256`、`<asset>.sha256sum`、`SHA256SUMS`、`sha256sums.txt`、
     `checksums.txt`（**只认与目标资产对得上的**；别的文件的 `.sha256` 不命中，避免"恒 mismatch"）；
  3. 两者都没有 ⇒ 明确 `null`，**不猜**。
- 下载后**真的比对 hash**。状态机（可在工具 notes 与返回值里看到）：
  | `verified` | 含义 |
  |---|---|
  | `'ok'` | 官方摘要（API `digest` 或发布页校验文件）匹配 |
  | `'pinned'` | 只有**内置 TOFU pin** 且匹配（见下） |
  | `'unavailable'` | 三种来源都没有 ⇒ 本次**没有校验**（会出现在 `ensureTools` 的 notes 里，不再隐身） |
  | `'mismatch'` | 不匹配 ⇒ **拒绝安装** |
  | `null` | 安装目录里已有二进制，本次没下载 |
  另返回 `digestSource`（`github-api` / `release-file` / `builtin` / `null`）与一句话 `verifyNote`。
- `FALLBACK_X86_64`（18 个硬编码兜底 URL）逐个**真实下载并计算 sha256** 作为内置摘要。
  **诚实标注**：内置摘要是 **TOFU pin（trust-on-first-use）** —— 只保证「与钉住的那一份一致」，
  **不证明上游未被入侵/未被替换**；所以记 `'pinned'` 而不是 `'ok'`，任何文案都不得把它说成"官方已验证"。
  18 项里有 5 项与官方来源**逐字相等**（ripgrep=官方 `.sha256` 文件；ast-grep / sd / bat / difft=API digest），
  其余 13 项该 tag 上游未发布任何摘要 ⇒ 只能 TOFU。
- 端到端实测（WSL，临时 installDir）：`bat`→`ok/github-api`、`rg`→`ok/github-api`、
  `tokei`→`pinned/builtin`（API 该版本 0 资产，真走兜底）、`taplo`→`unavailable`（真无摘要）；
  装出的二进制均能运行。`release-file` 路径当前没有"最新版无 digest 但有校验文件"的上游样本，
  由**本地 http 服务 + 真 curl + 真 hash** 的离线集成测试覆盖三种结局（匹配/不匹配拒绝/文件不覆盖资产降级）。

## 2. F-50：进程扫描失败不得被当成「没有进程」

`scanDaemonProcesses()` / `scanDaemonProcessesAsync()` 原来 `catch { return [] }`。于是「扫描失败」
与「一个守护都没有」在返回值上**完全一样**，而调用方全都拿它当证据：
`ensureDaemon` 据此删活守护的元数据（⇒ 隐形孤儿）、`waitForSlotGone` 返回 `[]` ⇒ `stopDaemon` 认为
「已停干净」并删元数据 + 报成功、`stopAllDaemons` 得到 `remaining.length === 0` ⇒ `ok:true`（伪成功）、
`daemonSnapshot` 得到空 `orphans` ⇒ 上层说「没有孤儿」。

现在：
- 扫描结果 `{ ok, procs, error? }`，`ok:false ⇒ procs 恒 []` 且**不代表没有进程**（async 入口可注入
  runner，便于离线单测；`scanResultOf()` 是纯函数）。
- 所有调用点按「失败 ≠ 空」重写：**扫描失败绝不删元数据、绝不判死、绝不发信号**。
- `stopDaemon` 新增 `verified`：`ok:false + verified:false` = 「无法确认是否停干净」，
  **不再**与「确认仍在跑（alivePids）」混为一谈；两者都保留元数据。
- `stopAllDaemons` 新增 `verified` / `scan` / `remainingCount`（失败时 `null`，**不是 0**）/ `subFailures`。
- `daemonSnapshot` 新增 `scan:{ok,error?}` 与 `orphansVerified`，`daemonStatus` 全分支透传。
- 工具面接线：`wsl_status` / `wsl_daemon status` 在扫描失败时打 `daemon scan: ⚠️ …` 告警，
  机器行的 `orphans=` 变成 `unknown` 并加 `scan=failed`（脚本不会再把未知读成 0）。
- `src/selftest.ts` 的 `race` / `reclaim` / `linger` 在扫描失败时**显式 FAIL**，不再拿空数组当"通过"。

## 3. F-32 / F-33：执行层的静默丢尾与终止原因

`runWsl()` 返回值扩展为
`{ exitCode, stdout, stderr, timedOut, aborted, truncated:{stdout,stderr}, killedBy, killedBySignal }`：
- **F-32**：每流 200KB 上限原来**静默丢尾**。现在 `truncated.*` 只在**真的丢过字节**时为真
  （"正好 200000 字节、一个字节没丢"不会被误报）；`wsl_exec` 把「流层截断（尾部已丢）」与
  「展示层只保留前 100000 字符」分开标注。同型缺陷在 daemon 侧也修了：`search-provision.runAsync`
  与 `search-rpc.spawnCollect`（`grep`/`glob` 的输出收集）—— 后者原来 stderr 按"块数 < 200"限，
  且 `truncated: outBytes >= maxBytes` 会把正好满误报成截断。
- **F-33**：原来用 `finish(124)` 表示超时、`finish(130)` 表示中断，于是**命令自己 `exit 124`**
  （`timeout(1)` 的既有约定）与「插件把它杀了」不可区分。现在 `killedBy` 由**我们自己的**定时器 /
  abort 监听决定（`timedOut > aborted > 退出码`），`{code:124, timedOut:false}` 必然得到
  `killedBy:'exit'`；`wsl_exec` 的首行按 `killedBy` 渲染（超时/中断/信号/命令自身退出码），
  `index.ts` 后台预热与 `wsl_sync_version` 的失败信息也一并区分。
- 另外把结算从 `exit` 改到 `close`（Node 文档明写 `exit` 时 stdio 可能仍开着），并加**有界**排空窗口
  （30ms 静默、总量封顶 1s）—— 后台进程占住管道时不会把正常结束拖成假超时。

## 4. `fs.listDir` 的符号链接语义（与上游 `dsh-fs-local` 对齐）

旧实现用 `lstat` ⇒ 任何符号链接都报 `type:'other'`；上游 `listDirectory()` 是「子项身份 =
realpath(链接目标)」+「元数据 = stat(跟随链接)」，所以 `ln -s /etc d` 在上游是 `directory`、
在本插件旧实现里是 `other`（面板显示成未知，`dsh-tool-fs` 的类型过滤也会漏掉）。

现在 `listDirOp` 照上游两步走：链接先 `realpath` 求身份（悬空链接退回链接自身，**不丢条目**），
再 `stat` 求类型/版本/大小；每个 entry 返回 `targetKey`，宿主 provider 用它（而不是
`path.posix.join(parent, name)` 现拼）—— 否则同一文件会得到两个身份，`contains()` 与
observation-policy 都会判错。性能实测（2003 项）：本实现 116ms / 旧 lstat 164ms /
无条件 realpath 254ms，即**语义对齐同时更快**（dirent 已说明是不是链接，只有链接才 realpath）。

## 5. 守护自身的三个真实缺陷（集成测试实测，本轮顺手修掉）

1. **EPIPE 会把守护打死并留下垃圾**：`log()` 的 `process.stderr.write` 不在 `try/catch` 里、也没有
   `error` 监听 ⇒ 启动它的包装层/父进程关掉 stderr 管道后，下一次写日志抛 EPIPE，进程 `exit 1`，
   **跳过 `cleanupFiles`**（元数据与 token 残留）。实测复现：`child.stderr.destroy()` 后触发一次日志
   ⇒ exit 1 + 残留。修法：写入包 `try/catch`、`stderr/stdout` 挂空 `error` 监听；日志写不出只写文件。
   这条与「关客户端 ≠ 会话结束」直接相关 —— 原来只要读者消失，守护就死。
2. **「启动 1.5s 后后台补齐核心 CLI 工具」是死代码**：它在 `listenOn()` 的 `return new Promise(...)`
   **之后**，从未执行过（注释与 README 都声称会预热）。实测：跑 4s 没有任何 provision 记录。
   修：移到 `main()` 里 listen 成功之后调用，并加一行可观测日志（`后台工具补齐完成：就绪 8/8`）。
3. **`--proxy-port 0` 与代码里的 0 分支自相矛盾**：`numArg('proxy-port', 9910, 1)` 把 0 判非法，
   而 `resolveProxyHost()` 有 `port<=0 ⇒ disabled` 分支 ⇒「0 = 关闭代理探测」不可达。已把下界改 0。

另新增 `--no-provision`（关掉启动时的后台补齐）：集成测试/CI 需要**零网络**确定性运行。

## 10. 追加：v0.3.2（真机 `wsl_agent` 首次跑通时发现的"错误丢失"）

0.3.1 之后重启 DSH，宿主加载 0.3.1、守护 `plugin=0.3.1 protocol=v2`，`wsl_exec` 的终止原因与两层截断
都在真机上对上了。但**第一次真跑 `wsl_agent`** 时它回了「本轮没有产出正文，可直接重试」——
翻 WSL 侧的会话事件流（`session.v4.jsonl.zstd` 解压）才发现真因是上游 `turn/end` 里明确报了
`AUTH 401: Authentication Fails, Your api key: ****3e11 is invalid`，被我们丢了。两个缺陷：

1. **`turn/end` 的上游错误被丢弃**：`sdk-runtime.route()` 只把 `completedBy` 记成 `'turn/end'`，
   没读 `data.reason.error`。于是"凭据无效"被念成"没有正文、可重试"，用户会一直撞同一堵墙。
   修：新增纯函数 `turnEndErrorOf(ev)` 抓 `{message, code, status}`；守护形态下若本轮无正文且
   上游明确报错，返回 `retryable:false` + 上游原话 + `errorCode`（运行时不销毁，改好凭据后同一 key 续上）。
2. **由此引入又被当场抓到的伪成功**：守护用 `ok: !retryable` 计算成败，`retryable:false` 一出现就把
   "失败"报成"成功且空答案"（`wsl_agent` 输出只有元信息、既无正文也无错误）。修：把判定收敛成纯函数
   `promptOkOf(r)`（带 `error` 一律算失败）并补单测；`wsl_agent` 的提示也按 `retryable` 分叉，
   不再一律写"可直接重试"。

实测（真守护 + 真上游，WSL 侧凭据当前确实失效）：
```
[remote-wsl: 本轮失败；运行时保持不动，但**不要原样重试**… retryable=false]
远端运行时在上游侧失败（AUTH 401）：Authentication Fails, Your api key: ****3e11 is invalid
（运行时保持不动；修好上游条件后同一 key 可继续，无需换 sessionId）
```

**这不是插件缺陷而是环境问题**：WSL 侧 `~/.dsh/.credentials.yaml` 里的 API key 已失效，
需要用户更新（Windows 与 WSL 各一份、不要跨侧复制）。插件现在会如实把 401 报出来。

门禁：`check-syntax` 27 TS + 13 JS；`node --test` **92** 条全过（新增 `test/sdk-runtime-turn-end.test.ts` 6 条）。

## 11. 追加：F-50 的 client 侧接线（面板可见面，不改版本号）

### 先纠正一个流传的说法
改前 `git grep -n orphans HEAD -- client/` **零命中**：面板从未消费 `orphans` / `orphansVerified` / `scan`。

## 12. 追加：`provider` / `model` 在 daemon 后端是**死配置**（2026-10-28，真机 401 逼出来的）

### 症状
WSL 侧 `wsl_agent` 每轮都回 `AUTH 401: Your api key: ****3e11 is invalid`。把 provider 改成另一个
OpenAI 兼容网关（`provider: commandcode` + 对应 model）后，**症状完全不变**，报错里也看不出 provider 是谁。

### 根因（调用链）
`config.ts` 的 `DEFAULTS` 里明明有 `provider` / `model`，`in-host-runtime.ts` 也真的把它们塞进
`initialize`；但**默认后端 daemon 这条路上，`daemon-launch.ts` 的 `launchScript()` 从不拼
`--provider` / `--model`** —— 守护于是用自己 `arg('provider','deepseek-official')` /
`arg('model','deepseek-flash')` 的默认值。于是：

```
用户配置 provider/model  ──✗（断在这里）──▶ daemon 启动参数 ──▶ dsh initialize ──▶ LLM 请求
                                        （in-host 后端才有这条路）
```

这是"配置项写了、执行路径没接线"的伪配置：**默认值恰好能跑**的时候，任何测试都不会发现它。

### 修法（提交 `41734ec`）
`launchScript()` 增加 `--provider` / `--model`（与 `daemon.ts` 的 `arg(...)` 严格同名），缺省回落到原值；
`JSON.stringify` 保证带 `/` 的模型 id（`deepseek/deepseek-v4.1-flash-fast`）不被 shell 拆开。
